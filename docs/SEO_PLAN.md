# Tokentracky SEO and blog launch plan

**First release objective.** Someone searching for an AI coding token leaderboard should land on the live board, understand what its numbers measure, and find out how to join. Someone evaluating the software should be able to read how the collector works and inspect the source. Someone curious about Token Town should find an accurate account of the game and where they can play it.

## 1. Decide which URLs belong in Search

Keep the existing leaderboard at the root. The public README and shared links already send readers there. Give installation, editorial content, and account actions distinct destinations.

| Route family | Proposed behavior |
| --- | --- |
| `/`, `/leaderboard` | Index `https://tokentracky.com/`. Use a permanent redirect from the duplicate `/leaderboard` path, preserve supported query parameters, and update internal links. Give the board an explicit heading such as “AI coding token leaderboard” and explain the period, units, and client-reported nature of the rankings. |
| `/join`, `/support`, `/privacy`, `/terms` | Serve indexable, self-canonical HTML for each. Put supported platforms and installation paths on `/join`, troubleshooting on `/support`, and the actual policy text on the legal URLs. Give each page its own title, description, and heading. |
| `/blog`, `/blog/<slug>` | Index the hub and published articles. Use one stable, lowercase, hyphenated URL per article. Unknown slugs and unpublished drafts return 404 to the public. |
| `/u/<alias>`, `/wrapped/<alias>/<period>`, `/vs/<a>/<b>` | Default share pages to crawlable `noindex` and omit them from the sitemap. Keep public share links and social previews working. Consider indexing profiles later if members understand search discoverability, public data is substantial, and withdrawal reliably removes it. Keep generated comparisons and wraps out of discovery. |
| `/you`, device connection, sign-in and recovery | Use `noindex` for account pages and server-identifiable callback requests. Keep sensitive responses private and uncached. Preserve the existing root callback, including fragment-based recovery and `/?connect=…`. Fragments never reach the server. Keep root HTML anonymous and let the client finish those flows. |
| APIs, README badges, cards, generated social images, preview deployments, and desktop views | Exclude from the page sitemap. Preserve embed and preview functionality. Apply `X-Robots-Tag: noindex` where standalone generated assets should stay out of Search. Keep article images, styles, and scripts fetchable. Protect private deployments or serve a deployment-wide `noindex`. Desktop-only views remain outside the public route list. |

Use the production HTTPS origin in canonicals, sitemap entries, and internal links. Canonicalize equivalent tracking, filter, and time-window views to the clean landing URL where applicable. Preserve what the person selected and existing referral attribution. Use a real 404 for an unknown, withdrawn, or private profile and 5xx for a temporary backend failure. Enforce visibility on the server and invalidate cached HTML and previews on withdrawal. Crawlers must be allowed to fetch pages that carry `noindex`. Google's October 2026 guidance specifically addresses platforms with user-created pages shared by link. [User-generated content](https://developers.google.com/search/docs/monitor-debug/prevent-abuse) · [Canonical URLs](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls) · [Indexing controls](https://developers.google.com/search/docs/crawling-indexing/block-indexing)

## 2. Make the public pages readable and discoverable

1. **Start with `/join` as an end-to-end test.** Generate its HTML at build time from the same copy the reader sees. Include a unique title such as “Install Tokentracky and join the AI token leaderboard”, a short description, a self-canonical, an H1, installation instructions, and real links. A direct HTTP GET must contain those elements even when the health endpoint is unavailable. Then apply the pattern to support, legal pages, and the blog.
2. **Keep the board live.** Return the board heading, explanation, and navigation in the first response. Render a small set of current public standings with their period and timestamp when the existing public data service is available. Refresh rankings and filters interactively. On a data outage, show that standings are unavailable and avoid displaying fabricated zeros or stale personal records.
3. **Make destinations links.** Use ordinary anchors for the brand, leaderboard, installation guide, blog, articles, and links between them. Retain buttons for actions such as filters and account submission. Make the path from board → installation guide → open-source walkthrough work with JavaScript disabled. Serve the same substantive content and HTTP status to readers, search engines, and social preview clients. Preserve per-page Open Graph cards.
4. **Publish discovery files.** Generate `/sitemap.xml` from the published route list and article metadata. Include only canonical, indexable 200 URLs. Set `lastmod` only when a page changes meaningfully. Serve `/robots.txt` as plain text and list the absolute sitemap URL. Verify direct deep links on the production host and any supported standalone server.
5. **Keep mobile pages fast.** Separate public content from desktop, game, and account initialization. Size screenshots explicitly, serve responsive images, and lazy-load below-the-fold media. Measure the board, join page, and one illustrated article. Target p75 LCP ≤ 2.5 s, INP ≤ 200 ms, and CLS ≤ 0.1 for mobile and desktop field data. Use lab diagnostics until traffic is sufficient for field reporting.

Google can render JavaScript. Returning meaningful initial HTML removes a dependency on a successful second rendering step. Descriptive titles, searchable text, and crawlable links also apply to AI features in Search. ## 3. Launch the blog

Use the existing web build to publish version-controlled articles. The hub needs a short introduction and, for each published story, a linked title, summary, byline, and date. Each article needs semantic HTML, an identifiable author, a publication date, sources, and a relevant next step. Generate the hub, sitemap, and matching `BlogPosting` JSON-LD from the same article records. Include headline, author, publication date, representative image where available, and modification date for substantive revisions. Validate a published example with Google's Rich Results Test. Start with a single index page and add pagination when readers need it.

| Publication order and proposed slug under `/blog/` | Reader question and original material | Next step |
| --- | --- | --- |
| **Launch — How Tokentracky counts AI coding tokens**, `how-tokentracky-counts-tokens` | “Can I inspect how this open-source tracker gets its numbers?” Trace a synthetic Codex session through the public collector. The forked-rollout fixture totals 550 input and 55 output tokens. Show why opening a fork with copied counters does not add the parent's usage twice. Link the fixture, expected output, MIT license, and public issue tracker. Identify which components run locally and which the project hosts privately. | Inspect the fixture, then try the private dashboard via `/join`. |
| **Launch — What becomes public when you join the leaderboard?**, `what-joining-the-leaderboard-shares` | “Will someone see my prompts or projects?” Show one example of a local session and the aggregate it contributes after device approval. Explain eligible historical usage, tool and model totals, estimated costs, and why some local history is excluded. Use synthetic records and link the privacy policy. | Review the publication details, then decide whether to join. |
| **Game launch — Token Town from first harvest to first building**, `token-town-first-harvest` | “What is the game, and how do I start?” Follow one town from eligible published usage through collecting resources to building or claiming adjacent land. Use three captioned screenshots from the same build and identify the platform, version, and entry point. Check the harvest rules and UI against that release. If still in development, publish an explicitly dated developer diary at its own slug and reserve this guide for launch. | Open the verified game entry point, or link a development diary to the project update. |
| **Follow-up — How to read the AI token leaderboard**, `how-to-read-the-token-leaderboard` | “Why do my weekly and all-time ranks differ?” Annotate one dated board example, change the period, and explain how token totals and estimated costs are calculated. Cover what a client-reported rank can tell a reader. | View the live board with the same period. |

**Suggested opening for the first article.** “A forked Codex session can start with a copy of its parent's counters. Add up every counter you see and the same work appears twice. In Tokentracky's public test case, the correct total is 605 tokens. Here's how to follow those 550 input tokens and 55 output tokens from a synthetic session record to the final count.”

Link the counting article from `/join` near the explanation of tracking, and the privacy article beside the explanation of publishing. Once the game is available, link its guide from the actual game entry point. Review articles when releases change a mechanic, supported platform, or publication rule. Use reader questions and Search Console queries to choose subsequent articles. Every article should contribute a worked example, original observation, or first-hand image. ## 4. Verify the release and measure the outcome

| When | Owner | Completion check |
| --- | --- | --- |
| Before implementation | Site owner | Verify the domain property in Search Console. Save the prior 28 days of clicks, impressions, CTR, and top queries by landing page, split by device and branded/nonbranded searches. Record Page Indexing exclusions and available Core Web Vitals. Mark missing data as unavailable. |
| First deployment | Web maintainer | Test direct requests to every evergreen page, one referral URL, the board duplicate, an account URL, a missing alias and a missing article. Check redirect targets, statuses, titles, headings, canonicals, robots directives, and HTML anchors. Verify sign-in, recovery, device approval, filters, sharing cards, and profile withdrawal still work. |
| Blog launch | Editor and web maintainer | Publish the hub and the two release-independent articles. Verify that readers can reach each from the board, open the fixture, and follow its next step. Crawl the sitemap and check that every entry is a canonical 200 with visible content. Submit it to Search Console and inspect the home, join, and article URLs, including Google's rendered HTML and selected canonical when available. |
| First month and monthly thereafter | Site owner and editor | Review indexing and unexpected URLs weekly for the first month. Compare successive 28-day periods for relevant queries and impressions, clicks to guides, and visits from articles to `/join` or the board where aggregate measurement is available. Distinguish an install-link click from a completed install. Inspect a page with impressions but few clicks for a mismatch between query, title, and content. Recheck Search Central updates when platform guidance changes. |

Engineering acceptance is verifiable at deployment. Indexing decisions, rankings, and traffic changes require subsequent observation.
